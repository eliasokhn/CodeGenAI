# Security model: executing untrusted generated code

CodeGenAI executes Python written by a language model (and, during the dataset audit, code from a
third-party dataset). Every such execution happens **only** inside a hardened Docker container.
The host Python process never `exec`s, `eval`s or imports generated code; the only host-side
operations on it are `ast.parse`/`compile` (syntax check without execution) and string handling.

## Threat model

| Threat | Mitigation |
|---|---|
| Network exfiltration / downloads / DoS from generated code | `--network none` (verified: `socket.create_connection` -> `OSError: Network is unreachable`) |
| Tampering with the image / persistence | `--read-only` root filesystem; the only writable paths are RAM-backed `tmpfs` mounts (`/work`, `/tmp`) with `noexec,nosuid,nodev` and size limits, destroyed with the container (`--rm`) |
| Privilege escalation | `--user 1000:1000` (non-root, verified `os.getuid() != 0`), `--cap-drop ALL`, `--security-opt no-new-privileges` |
| Fork bombs / runaway processes | `--pids-limit 64`, `--init` (zombie reaping), `ulimit cpu` equal to the run timeout |
| Memory bombs | `--memory 256m --memory-swap 256m` (no swap); OOM kill is reported as `runtime_error` |
| CPU hogging / infinite loops | `--cpus 1.0`; per-test `pytest-timeout` (5 s, signal method); whole-run wall clock timeout (20 s) enforced by the host followed by `docker kill` |
| Output floods | container stdout/stderr read incrementally and capped (`max_output_bytes`, 64 KiB); in-container report tails are capped; `ulimit fsize` 10 MiB |
| Escaping via mounts | no bind mounts, no volumes, **the Docker socket is never mounted**; the payload (source files) is sent over **stdin** as JSON and written by the runner into the tmpfs work dir |
| Secrets leakage | the container environment contains only `PYTHONDONTWRITEBYTECODE`, `PYTHONHASHSEED`, `HOME`; no API tokens or host environment variables are forwarded |
| Path traversal in payload file names | runner and host both reject names with path separators, hidden files and non-`.py` suffixes |
| Unsafe fallback when Docker is missing | **none**: `get_sandbox()` returns a `DisabledSandbox` whose every run is `Status.UNAVAILABLE`/`verified=False`; the app labels such output *unverified*; the evaluator refuses to run (`require=True`) |

The exact `docker run` argument vector is generated by `DockerSandbox.docker_command()` and is
asserted in `tests/test_sandbox.py::test_docker_command_enforces_hardening`. Integration tests
(`@pytest.mark.docker`) execute probes inside the real container to confirm non-root execution,
no network, read-only root fs, absence of `/var/run/docker.sock`, timeouts and output truncation.

## Image

`docker/sandbox/Dockerfile`: `python:3.11-slim` + pinned `pytest==8.4.2`, `pytest-timeout==2.4.0`,
`numpy<2` (only needed by MBPP+ test scripts). `pip` is removed after installation. The runner
script `/opt/runner/runner_entry.py` is root-owned and read-only; Python runs in isolated mode (`-I`).

## Data-flow isolation (research validity)

* Hidden MBPP tests are executed in a **separate container run** from the feedback (visible)
  tests; the correction loop's runner can only build `test_visible.py`.
* `TestReport.visible_failures()` is the only accessor the feedback formatter uses; hidden
  results carry `hidden=True` and are filtered. `assert_no_hidden_leak` re-checks every feedback
  string in the evaluator.
* Mock generators carry `is_mock=True`; `MBPPEvaluator.evaluate_configuration` raises if one is
  passed, so software-test doubles can never produce research numbers.

## Residual risks

* Docker Desktop on Windows runs containers in a shared Linux VM. Container escapes would require a
  kernel/runtime vulnerability; keep Docker Desktop updated. gVisor/Kata are not used.
* The `--cpus` and memory limits rely on cgroups inside the Docker VM; they bound, but do not fully
  prevent, host resource pressure on a laptop.
* The dataset audit executes third-party dataset code (KodCode tests/solutions) under the same
  sandbox; the static import filters additionally exclude network/OS/subprocess modules from
  training data, but the sandbox, not the filter, is the security boundary.
